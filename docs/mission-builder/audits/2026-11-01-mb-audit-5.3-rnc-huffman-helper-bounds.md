## Verified assembly findings
- make_huftable begins at lines 62448–62522. It reserves 0x10 (16) bytes of temporary stack storage at 62452, sets EDI to that stack area, reads a 5-bit value via input_bits at 62454–62457, and, if nonzero, repeats a 4-bit read and single-byte write at 62460–62465 exactly that many times.
- A 5-bit count has a possible numeric range of 0–31. This routine does not visibly reject values above 16 before writing to its 16-byte scratch area. Thus malformed bitstreams can cause an out-of-bounds scratch write. The valid RNC encoding may impose further format constraints, but the routine does not enforce them in this path. No actual malformed-input test or exploit was performed.
- The same routine subsequently constructs Huffman table entries using STOS word operations and a fixed offset write at 62503; this audit has not established the destination table's complete allocation capacity. Avoid claiming an additional overflow without checking the corresponding table declarations.
- input_value at 62370–62396 searches Huffman table entries based on bit-buffer comparisons and draws additional bits from input_bits. No verified physical compressed-source length is supplied to it.
- input_bits at 62400–62444 advances the compressed-data pointer and reads 16-bit words at 62424–62425, without comparing the source pointer to an independently known buffer end.
- The caller UnpackM1 at 62291–62297 invokes make_huftable three times per block. Its source and destination pointer-only interface cannot independently enforce actual input size or output allocation capacity, as established in MB-AUDIT-5.2.

Coordinate loader work with the mainline RNC audit; the assembly decoder must not be silently replaced with the distinct C implementation.
