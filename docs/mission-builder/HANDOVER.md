**Do not conflate the two objective systems.** The packed C `CPObjective` struct (game_data.h lines 34–45) has 15-byte stride and the engine allocates `level__CPObjectives[128]`, 0x780 = 1920 bytes (syndre.sx ~85798–85799). `init_computer_players` at ~7051–7078 iterates 128 records, clearing flag bit 0x10 at record offset 6; `CPDoTurn` ~7604-7625 indexes these records using 15-byte stride; `CPGetObjective` ~9364 onward searches them; `CPGetFirstObjectiveInList` ~9741–9757 follows links via 16-bit offset 2. Evidence ties these to computer-player actions/orders; they must NOT be presented as the player's mission win conditions. Full semantics of all CP action types/target pointers remain unverified, as do safe authoring limits.

**Actual player mission completion evaluation** is a separate path in `check_end_level` (~531–1167). It loops 8 entries using stride 0x0e (14 bytes), checks a 16-bit type field at entry offset +4 (`data_9be3e`), dispatches types 0–16 through `vtable_10550` at ~491–509, updates a 32-bit completion state at entry offset +0 (`level__Objectives`) and examines 8 states for equality to 1 (~1101–1130). The region `level__Objectives` at ~85770 through `level__ComputerPlayersCount` at ~85782 is 0x70 = 112 bytes, consistent with 8 x 14-byte entries. The second 16-bit field at +6 (`data_9be40`) is used in multiple handlers as an offset into the `level__things_base` entity data, but its full reference semantics and other fields remain unverified. Some type handlers call `level_failed`, and all-complete calls `level_complete`. This is evidence of an actual mission win/fail objective interpreter, not yet a safe editable or serializable format.

**Builder scope / implementation gate:** define separate specifications for (A) eight-entry player mission objectives and (B) computer-player orders/behaviour. Do not expose raw numeric objective types or offset fields as editable until constraints, reference validation, unused-entry behaviour and original RNC resource layout are understood. Do not infer that the full 128 CP records can be used for authored objectives or that unrecognized player objective types can be written. Next: document all active mission objective type handlers and dependencies, then implement a read-only inspection/validation prototype against synthetic test data before any write-capable editor. Existing missions and tactical behaviour protected. No source modifications, build or gameplay tests in this audit.
