## Source evidence
engine/src/syndre.sx (blob c35e22621a93d1e07c44d40de8867446ff7c64bf):
- Lines 85164–85169 allocate three separate 0x80-byte regions: unpackm1__raw_table, unpackm1__pos_table, and unpackm1__len_table, each 128 bytes. They are consecutive, fixed-size regions.
- UnpackM1 calls make_huftable for these three pointers at lines 62291–62297.
- make_huftable at lines 62450–62465 reserves 0x10 (16) stack bytes, reads a 5-bit symbol count via input_bits, then writes a 4-bit length byte for each symbol. There is no explicit count<=16 test. A 5-bit count can represent 0–31, but whether valid RNC data ever supplies >16 is NOT established by this source examination.
- In the construction loop at lines 62474–62516, STOS operations and a write relative to EDI+0x3c populate the destination table. The table has only 128 reserved bytes, but this audit has not computed a proven maximum byte offset over all possible Huffman code-length sequences. Do not claim a specific table write exceeds that allocation without deeper reachability and offset analysis.

## Interpretation
The scratch-array concern from MB-AUDIT-5.3 is reinforced by fixed-size storage, while the table allocation itself is now concretely identified. The maximum legal symbol count, maximum table writes, and actual behavior with valid resource data remain unverified. The three tables have distinct roles but the same reserved capacity; changing the layout or decoder would affect shared legacy resource behavior.
