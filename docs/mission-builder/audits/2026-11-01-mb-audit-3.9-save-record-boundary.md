## Source-derived integrity and gameplay implications
- load_player opens save/%02d.gam then reads all seven segments without checking individual byte counts; corrupted/truncated files can partially overwrite live state. The first 20 header bytes are read into the start of players as temporary skip-space before the actual players block overwrites it; this is unusual but not a separate format field.
- save_player deducts 10% of credits when >30000 before attempting LbFileOpen. If opening fails, source returns false but the in-memory credit deduction has already occurred. This is a source-confirmed error-path side effect, not a tested runtime incident.
- save_player does not check individual LbFileWrite results or close status and returns true after an opened file. Partial writes can therefore be reported as successful. The 10% legacy credit rule must not be changed in an audit-only phase.
- load_save_text enumerates just a 20-byte description, not the full record, so file presence and text do not prove 28,247-byte integrity, campaign identity or compatibility.
- These functions have no campaign identity argument, and filesystem resolver discrepancies remain as per MB-AUDIT-2.4–2.9.
