# MB-AUDIT-5.2 — Assembly UnpackM1 input/output extent audit
Date: 2026-11-01 (Australia/Brisbane)
Branch: feature/mission-builder-audit
Status: static audit only.
Previous: docs/mission-builder/audits/2026-11-01-mb-audit-5.1-rnc-assembly-contract.md

## Source examined
engine/src/syndre.sx, blob c35e22621a93d1e07c44d40de8867446ff7c64bf, lines 62225–62455 and the previously documented assembly briefing caller.

## Findings
1. UnpackM1 uses source and destination pointers at 62236 and 62251–62253. No explicit source byte-count or output capacity argument is supplied.
2. Signature verification at 62237–62242 accepts the expected RNC marker. Failing this path returns EAX=0 with carry set (62345–62350).
3. The function extracts declared unpacked and packed lengths using blong at 62243–62246 and derives pointers from those lengths at 62250–62262. An overlapping input/output relocation branch uses reverse copying at 62263–62283. Pointer arithmetic cannot independently verify that the allocation or read actually covers those lengths.
4. Raw output and backreferences use rep movsb at 62303–62321. The inspected function has no explicit capacity-based check on EDI/output extent or source input bound before these copies. Bitstream reading at 62400–62444 loads words via ESI without a verified physical source-end comparison in this inspected routine.
5. On completion, code at 62337–62344 returns the header-declared unpacked length in EAX with carry clear. This is an algorithm completion path, not validation of actual file length or destination allocation. Underlying malformed input might also cause different behavior before completion; no fault testing done.
6. LbFileReadRNC (14916–14960) calls assembly UnpackM1, checks the signed EAX result but not carry, and ultimately returns its saved file handle, not an actual decoded byte count. load_text (55249–55289) does not inspect that return and writes its terminator based on LbFileLengthRnc. The assembly helper and common C decoder must not be assumed ABI-compatible.

## Risk boundaries
There is a source-confirmed absence of independent length enforcement in the inspected assembly path. That does not establish that valid retail data overflows or that a runtime crash was reproduced. briefing buffer brief_text has 4000 bytes; valid null-terminated text requires an explicit maximum of 3999 output bytes unless a different storage contract is proven.

## Test gate before modifying anything
In a disposable Windows build with known-good assets, compare decoded length against physical file size, header-declared size and output capacity. Include header-only files, truncated compressed data, mismatched packed lengths, zero/large declared output, invalid signature, invalid bitstream and valid mission briefing fixtures. Inspect destination canaries and source read counts. Avoid modifying saved games or shipping resources. Record any difference between DOS/SDL and native assembly/C paths.

## Handover
Documentation-only on the Mission Builder branch. No source modifications, compilation, runtime checks, fuzzing, retail-resource tests, save writes or mainline changes. Next: inspect all directly invoked helpers and distinguish additional decode-internal constraints from the absence of a public buffer-size contract; coordinate with mainline RNC audit before implementation.
