## Measurement interpretation and limitations

- This is **C-side pacing instrumentation**, not yet a full explosion profiler. `update_ms` covers the duration of `game_update_full` itself, not entire tactical tick or rendering/simulation preceding it.
- `event_ms` times the **initial** SDL event pump within the call. More event pumps can run inside the conditional wait phase and are included in `wait_ms`, not individually counted.
- `wait_ms` includes scheduler work, delays, event pumps and locking during the phase from immediately after initial event pump until final pacing return. It is **not strictly sleep time**.
- All values are aggregate totals and averages, not individual frame latency distributions or per-explosion cost. The record is printed when `game_quit` is executed, so an abnormal process exit may not write the log.
- This instrumentation must **not** be treated as an automatic performance improvement or as evidence against any hypothesized collision/renderer/audio bottleneck.
- Timing overhead is disabled in ordinary `main`; the standalone diagnostic branch does call a few high-resolution timer functions per frame.

## v0.7-D1 additional whole-interval telemetry (2026-11-07)

Commit `34f80cbe9e154a15f19ba11b7b8fbb39abf28984` extends `engine/src/game.c` with a bounded record of the elapsed time between successive calls to `game_update_full` **in the same mode**. It records the count, average, maximum and count above 62, 125 and 250 ms. Mode switches are excluded. This interval includes preceding pacing and intervening simulation/rendering, so it can flag a slow tactical frame without changing any assembly gameplay logic.

It does **not** isolate explosion effects or distinguish a long intended wait from rendering and simulation costs. The 62 ms threshold is useful for tactical 16 FPS but should not be used to classify menu 30 FPS frames as late. No per-frame logs or exact percentile distribution are recorded. The added fields are `between_n`, `between_avg_ms`, `between_max_ms`, `between_gt62`, `between_gt125` and `between_gt250`.

## v0.7-D1 C-side non-pacing work decomposition — 2026-11-07

Commit `5cd25c036b79a4851444bf87eab68e0cc18e1c40` adds **outside-update elapsed time**. The initial 16/30 FPS C `game_update_full` timers covered only the pacing/event loop, while the existing `between_*` counters encompassed both the preceding C pacing phase and intervening work. The new `outside_*` metric measures from the previous `game_update_full` **return** to the next same-mode `game_update_full` **entry**. It therefore excludes the previous C pacing function, and includes intervening legacy assembly control-flow, simulation/effects/collision, drawing, screen calls, and any other intervening work. It is not pure explosion time or an exclusive simulation clock.

New aggregate fields: `outside_n`, `outside_avg_ms`, `outside_max_ms`, `outside_gt16`, `outside_gt33`, `outside_gt62`, `outside_gt125`. Mode switches deliberately omit a sample; samples are not attributed across tactical/menu transitions. Durations and thresholds use SDL performance counter and frequency. No change is made to the tactical or menu frame wait policy.

**Interpretation:** `outside_gt62` indicates more than 62 ms spent *outside the pacing function* and is more meaningful than `between_gt62` for detecting costly world updates, but the threshold is not a proof of player-visible stutter or explosion causation. `outside_gt125` is a stronger candidate for problematic intervening work. Compare equal-duration quiet and overlapping-explosion scenes using repeated tests before prioritizing a fix. Values are aggregate totals, maxima and threshold counts, not per-frame timelines or percentiles. This probe does not separate `move_effects` from MapWho collisions, audio, screen conversion, or the SDL presentation path. It also cannot attribute individual explosions or establish a minimum/typical frame rate.

**Verification:** Source committed to diagnostics-only branch and must pass its own Windows CI head before being represented as compiled. Earlier successful run `42347706162` validated the previous `34f80cb` source, **not** this revision. No runtime data or gameplay test is claimed.
